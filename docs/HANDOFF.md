# esys-mcp(仮称) 引き継ぎメモ

BMW E-Sys を Claude から MCP 経由で操作するためのツール。リモートコーディング作業の E-Sys 操作部分を Claude に任せることが目的。オープンソースで公開予定。

この文書は構想段階の相談内容をまとめた引き継ぎメモ。「要確認」と書いた項目は未検証なので、推測で埋めずに実物で確かめること。(確認結果は `docs/phase0-findings.md` にまとめる。)

## 目的と運用イメージ

- 人間がやること: 顧客との連絡、リモート接続と VPN の準備、エージェント付きでの E-Sys 起動、書き込み前の最終承認
- Claude がやること: 車両への接続、FA/SVT とコーディングデータの読み取り、レシピの適用、変更内容(diff)の提示、承認後の書き込み、書き込み後の確認、作業記録
- 難しいコーディング(後付けで複数 ECU の整合が必要なケースなど)では、Claude が実データ(FA / SVT / NCD)を直接見て、パラメータの横断検索や「機能あり車両と機能なし車両の NCD の diff」で調査できるようにする
- Claude は FDL の全パラメータの意味を知っているわけではない。答えを出す役ではなく、探索と比較を高速でこなす役として設計する

## 決定事項

- 実装言語はすべて Java
- 構成は二段: E-Sys の JVM に差し込む薄いエージェントと、別プロセスの MCP サーバー
- 対象はまず F 系のみ。G 系は後回し(新しい I-Step ほどコーディング周りの制約が増える想定)
- 開発・検証用の車両は開発者の F31(F 系)
- MCP サーバーは E-Sys が入っている Windows 機でローカルに動かす(stdio)。MCP をネットワークに公開しない
- 車両とは、その Windows 機から VPN 越しに IP で接続する前提

## アーキテクチャ

### esys-agent(E-Sys の JVM 内で動く)

- E-Sys 起動時に `-javaagent:esys-agent.jar` で注入する(動的アタッチは使わない)
- E-Sys 同梱 JRE のバージョンに合わせてコンパイルする(バージョンは要確認)
- 依存は最小限にする。できれば JDK 標準のみ。外部ライブラリを持ち込む場合は shade でパッケージをリロケートし、E-Sys 側のライブラリと衝突させない
- エージェントが落ちると E-Sys も落ちる。コーディング中のクラッシュを避けるため、エージェント内のコードは最小限に保ち、重い処理はすべて MCP サーバー側に置く
- 127.0.0.1 限定で小さな RPC を公開する。起動時にランダムなトークンを発行してローカルファイルに書き出し、全リクエストでそのトークンを必須にする
- 公開する操作(案): getStatus / getVersion、connect(gatewayAddress)、readFA、readSVT、readCoding(ecu)、prepareWrite(...)、commitWrite(token)
- 書き込みゲート(後述の prepare/commit)は、このエージェント側で強制する。MCP サーバー側にバグがあっても勝手に書き込めないようにするため
- 起動時に E-Sys のバージョンを確認し、検証済みバージョン(allowlist)以外では書き込み系を無効にする
- Swing UI からの操作とエージェントからの操作がぶつからないよう、何らかの排他を入れる(方法は要調査)
- E-Sys の既存 API を呼ぶだけにとどめる。トークンやライセンスのチェックには触らない。バイトコードの書き換えも原則しない

### esys-mcp(MCP サーバー、別プロセス)

- Java 17 以上(MCP Java SDK の要求バージョンは要確認)、stdio トランスポート
- esys-agent とは localhost の RPC で通信する
- NCD/CAFD のパーサー、diff、横断検索、レシピ、ジョブ管理、MCP のツール定義はすべてこちら側に置く
- dry-run モードを最初から入れる

### モジュール構成(案)

```
esys-mcp/
  core/              NCD/CAFD パーサー、diff、検索、レシピ処理(Java 17+)
  server/            MCP サーバー(Java 17+)
  agent/             esys-agent(E-Sys 同梱 JRE のレベル、依存最小)
  examples/recipes/  レシピ書式のサンプル(公開用)
  recipes/           実運用のレシピ(.gitignore 対象、非公開)
```

ビルドは Gradle のマルチプロジェクトを想定(Maven でも可)。E-Sys の jar はビルド時の参照のみ(compileOnly 相当)とし、配布物には含めない。

## ジョブ(作業単位)

1 台・1 回の作業ごとにフォルダを切り、次のものをまとめて保存する。

- VIN、FA、SVT
- 作業前の NCD バックアップ
- 変更後の NCD
- 変更ログ(どの ECU / CAFD のどのパラメータを何から何に変えたか、適用したレシピ)
- 作業の要約

何かあったときに戻せることと、後から「この車に何をしたか」を追えることが目的。将来、外部の整備管理システムに履歴として取り込めるよう、素直なファイル形式(JSON など)にしておく。

## レシピ

- YAML で記述する
- 適用条件: シャシー、I-Step、CAFD のバージョン
- 変更内容: ECU / CAFD、パラメータ名、値
- 検証済みフラグを持たせる
- ツール側で「この車両にこのレシピを当ててよいか」を判定する
- レシピ外の変更を Claude が提案する場合は、必ず「未検証」と明示する
- 実運用のレシピは開発者のノウハウそのものなので非公開とする(recipes/ は .gitignore、または別のプライベートリポジトリ)。公開リポジトリには書式サンプルだけを置く

## 安全要件(外さないこと)

- 書き込みは prepareWrite と commitWrite の二段にする。prepareWrite は変更内容の要約と一回限りのトークンを返し、commitWrite はそのトークンがないと動かない。commit は人間の承認後にだけ行う
- 書き込み前に元の NCD を自動でバックアップする
- 電圧を読み、閾値を下回っていたら書き込みを拒否する(電圧の取得方法は要調査)。リモートでは先方の電源状況が見えないため特に重要
- 書き込み系の機能は初期状態で無効にし、設定で明示的に有効化する。有効化しても承認・バックアップ・電圧チェックは外せない作りにする
- 検証済み以外の E-Sys バージョンでは書き込みを無効にする
- TAL によるプログラミング(フラッシュ)は対象外。途中で失敗したときの被害が大きすぎるため
- dry-run モードでは ECU に一切書き込まない

## 公開に関する制約

- E-Sys 本体、PSdZData、トークン類、デコンパイルした E-Sys のコードは、リポジトリに一切含めない。利用者が自分の環境を用意する前提にする
- E-Sys の内部はクラス名・メソッド名を参照するだけにとどめる
- テストデータは開発者自身の車両のものだけを使う。顧客車両のデータ(VIN などを含む)はコミットしない
- ライセンスは Apache-2.0(2026-10-13 決定。GPL-3.0 も検討したが、agent がプロプライエタリな E-Sys の JVM 内で動くため、単純な Apache-2.0 にした)。README に「自己責任で使うこと、無保証」を明記する

## ロードマップ

ECU に書き込む処理は Phase 5 まで実装しない。Phase 1〜3 は車両に一切書き込まないので、安全に進められる。

### Phase 0: 調査

- E-Sys 同梱 JRE のバージョンを確認する
- E-Sys の起動方法を確認し、-javaagent を足せる場所(起動スクリプト、ランチャー)を特定する
- CFR か Vineflower で E-Sys をデコンパイルし、UI の裏で呼ばれているサービス層(接続、FA/SVT 読み取り、コーディングデータの読み書き)を特定する
- MCP Java SDK の要求 Java バージョンを確認する
- サンプルを集める: F31 で主要 ECU のコーディングデータを読み、NCD と PSdZData 内の対応する CAFD を一式そろえる。いくつかの ECU について E-Sys の FDL エディタで表示される値を控え、パーサー検証用の正解データにする

### Phase 1: NCD/CAFD パーサー(読み取りのみ)

NCD と CAFD から、パラメータ名と値の一覧を出す。FDL エディタの表示と一致するまで詰める。フォーマットは推測で埋めず、サンプルと正解データで検証する。

### Phase 2: diff と横断検索

2 つの NCD の diff と、パラメータ名の横断検索を実装する。

### Phase 3: MCP サーバー(読み取り専用ツール)

Phase 1〜2 を MCP のツールとして公開する。ここで初めてチャットから使えるようになる。

### Phase 4: NCD の書き換え

レシピを適用して NCD を書き換え、E-Sys がそれを受け付けるかを F31 で検証する。エージェント経由で直接書き込めることが分かれば、その経路の検証に置き換えてもよい。

### Phase 5: esys-agent

E-Sys の操作をツール化する。読み取り系(接続、FA/SVT、コーディングデータ)を先に作り、書き込み系は安全要件をすべて満たしてから実装する。
